- 每个模块都是「后端主 + 前端主 + 测试主」三角，缺一个不算完成。

## 6. 协作机制

### 6.1 节奏

| 时间 | 会议 / 动作 | 产出 |
| --- | --- | --- |
| 周一 30 分钟 | 计划会：认领本周任务、确认跨人依赖 | 每人一条「本周交付物 + 完成标准」 |
| 周三 15 分钟 | 同步会：只讲阻塞和依赖变化 | 阻塞项 + 当天解决方式 |
| 周五 30 ~ 45 分钟 | 验收会：按第 6.3 节逐条过，现场跑命令 | 通过 / 不通过 + 下周返工项 |
| 随时 | 单个问题卡超过 1 天 | 升级给 P1，写进任务卡 |

### 6.2 Git 与代码评审

- 分支命名：`feat/<模块>-<姓名缩写>`、`fix/<问题简述>`、`docs/<主题>`；不直接在 `master` 上开发。
- 提交信息用中文写清「做了什么」，一个提交只做一件事。
- 每个 PR 至少 1 人评审：模块内互评，触及公共层（认证、权限、数据模型）由 P1 评审。
- 合并前必须跑通第 6.3 节的回归命令。
- 不提交运行数据（`instance/`、`media/`）、不提交个人环境（`.venv/`、`.django-learning/`）。

### 6.3 完成标准（Definition of Done）

一个任务要算完成，六条都要满足：

1. 代码或文档已提交，分支已合并。
2. 有对应的自动化测试，或说明为什么这条不适用。
3. 相关文档同步更新（需求 / 接口规范 / 验收清单至少改一处）。
4. 页面功能在浏览器里实际走通过，不只是接口返回 200。
5. 有可复现的证据：命令输出、截图或复验记录。
6. 验收人（默认 P1）当场确认通过。

### 6.4 文档与口径

- `docs/` 是唯一权威来源；会上口头定的结论，当天必须落进对应文档。
- 需求和接口没冻结，不写业务代码；冻结后要改，由 P1 记录变更原因和影响范围。
- 每个模块完成后更新 `docs/README.md` 索引和 `README.md` 的当前状态。

## 9. 技术路线

- 项目实现框架：Flask 3（待第 7 节第 1 条确认；Django 仅作对照学习，不重复实现本项目）。
- 开发数据库：SQLite；生产环境按需切 PostgreSQL。
- 文件存储：本地 `backend/media/`，可按需切腾讯云 COS。
- 前端：静态 HTML / CSS / JS + Bootstrap 5，业务方向负责原型，后端提供 JSON API。
- 测试：pytest（后端）+ 浏览器走查（前端）。
- 部署：W10 确认后落地，候选为腾讯云轻量应用服务器或 SCF。

## 10. 协作边界

- 业务方向先确认页面和交互原型，需求与接口规范确认后技术后端再实现。
- 后端完成一个模块后，通过接口测试和联调验收，再进入下一个模块。
- 需求定义、原型评审和最终架构决策由项目负责人确认；后端按确认后的需求与接口规范实现。
