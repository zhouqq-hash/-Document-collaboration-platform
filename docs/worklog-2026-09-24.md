## 3. 设计要点

1. **两种模式而不是两套代码**：有没有配 `WECHAT_APP_ID` / `WECHAT_APP_SECRET` 决定走真实扫码还是演示模式，接口、数据库和前端页面完全共用，不需要为了演示另写一套假登录。
2. **state 一次性**：授权地址带随机 state，存进 session，回调时比对并立刻 `pop`，同一个 state 不能二次使用；伪造 state 直接判失败。（09-27 为了兼容微信 webview 不带 cookie 的情况，改成了「签名令牌 + session 校验」双路径，见那天的日志。）
3. **微信建号没有密码**：`password_hash` 允许为空，`check_password()` 遇到空哈希直接返回 `False`，所以微信用户既不能用工号密码登录，也不会因为拿到 `None` 报 500。
4. **绑定优先于建号**：老师原来有工号，用「账号设置 → 绑定微信」把微信绑到原账号，权限和负责的文档都不变；没有绑定才按 openid 建新账号。
5. **一个微信只绑一个账号**：`wechat_openid` 加唯一索引，应用层也先查再绑，冲突返回 409 并给中文提示。
6. **解绑要防自锁**：微信自动创建且没有密码的账号不允许解绑，避免解绑后彻底登不进来。

## 5. 今天定下来的决策

1. 微信登录默认走演示模式：课程演示和测评环境拿不到微信开放平台的应用参数，页面必须开箱可用。
2. 微信账号默认角色是 `teacher`（`WECHAT_DEFAULT_ROLE` 可改），不做自动管理员，避免扫码就拿到最高权限。
3. 微信登录只解决「怎么进来」，权限体系不动：进来以后还是管理员 / 负责人 / 普通教师三层。
4. 演示模式的接口在配好真实应用信息后自动返回 403，防止生产环境被模拟登录绕过。
